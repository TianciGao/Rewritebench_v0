# Generating Scripts Review

## Generator

The readiness files were generated by legacy `scripts/cli.py`.

Relevant legacy functions and parser:

- `sqlsolver_verieql_support_candidate_case_ids`
- `sqlsolver_verieql_support_readiness_assessment`
- `cmd_baseline_smoke_sqlsolver_verieql_readiness`
- argparse subcommand `baseline-smoke-sqlsolver-verieql-readiness`

## Command Contract

The parser supported:

```text
python -m scripts.cli baseline-smoke-sqlsolver-verieql-readiness \
  [--case-id CASE_ID] \
  [--candidate-set support-first|pg-native-9] \
  [--output sqlsolver_verieql_support_readiness_v0.json] \
  [--execute]
```

Default candidate set was `support-first`. The reviewed artifact used `pg-native-9`.

## Execution Refusal

The command explicitly refused `--execute` and wrote:

```text
reports/baseline_smoke/sqlsolver_verieql_support_readiness_execute_refused_v0.json
```

The refusal payload states the scaffold is read-only and never executes SQLSolver, VeriEQL, or an SMT solver.

## Static Signals Used

The readiness generator read case registry rows, manifests, and source SQL, then emitted static SQL-shape signals such as:

- aggregate
- comments
- correlated subquery risk
- date literal
- exists
- group by
- interval literal
- join
- limit
- nested select
- offset
- order by
- TPC-H/TPC-DS style tables
- window function

It hard-coded missing readiness flags:

- `sqlsolver_runner_available=false`
- `verieql_runner_available=false`
- `solver_dependency_available=false`
- `smt_solver_available=false`
- `schema_constraint_extraction_available=false`
- `timeout_policy_available=false`
- `subset_policy_available=false`
- `equivalence_execution_attempted=false`
- `support_analysis_attempted=false`

## Reuse Value

The old generator is useful as a candidate-selection and static SQL-shape signal reference. It is not a runner, not a verifier adapter, and not a source of official evidence.
