# Evidence Ledger Schema v1 Draft

Status: draft

Purpose: define the future canonical evidence ledger used by retained evidence adapters, metrics computation, report rendering, and user submissions.

This draft does not change metrics, paper results, denominator values, case membership, or case admission. It is not a result table yet. It is a schema direction for denominator-aware and role-aware reporting.

## Design Goals

- Use canonical case packages and `case_sets/common_core_v0/` as primary membership inputs.
- Represent retained legacy evidence and future user-run outputs through one normalized ledger shape.
- Keep denominator, route, method role, execution state, correctness state, timing state, and evidence provenance explicit.
- Support report rendering without depending on legacy report scripts as the governing architecture.
- Preserve unsupported, failed, missing-artifact, checker-failed, no-op/source-like, timing-missing, and exact/timed boundaries.

## Draft Row Grain

The expected ledger row grain is one candidate or control route observation for one case, engine, denominator row, and method role.

Examples:

- source control for `PERF_0006` on PostgreSQL;
- positive rewrite control for `CONS_0007` on Spark;
- hard-negative checker control for `PORT_0024` on MySQL;
- method-generated candidate for a case/engine route;
- retained legacy evidence row imported by adapter.

## Draft Fields

Required identity fields:

- `case_id`
- `pool`
- `case_set`
- `denominator_id`
- `engine`
- `route`
- `method_role`
- `candidate_id`

SQL and candidate fields:

- `source_sql_path`
- `candidate_sql_path`
- `generated`
- `ready`
- `parse_status`

Execution and correctness fields:

- `executed`
- `exact`
- `timed`
- `result_status`
- `failure_stage`
- `failure_type`
- `checker_status`

Observability and timing fields:

- `plan_available`
- `plan_artifact_path`
- `latency_ms`
- `speedup`
- `timing_eligible`

Evidence provenance fields:

- `evidence_source`
- `retained_artifact_path`
- `notes`

## Field Semantics

`case_id`: canonical case identifier from `inventory/case_registry.csv`.

`pool`: one of `PERF`, `CONS`, `PORT`, or `LONGTAIL` for Common-core v0 rows.

`case_set`: release case set such as `common_core_v0`.

`denominator_id`: stable denominator scaffold identifier, for example from `case_sets/common_core_v0/denominator_same_engine_120.csv`.

`engine`: one of `postgres`, `mysql`, or `spark` for public v0.

`route`: route being observed, such as `source`, `positive`, `hard_negative`, `same_engine_rewrite`, `portability`, or a method-specific route.

`method_role`: role-aware method label such as `control`, `direct_llm`, `repair_1`, `sqlglot`, `calcite_hep`, `r_bot`, `verifier_support`, or `retained_legacy_reference`.

`candidate_id`: stable row-level candidate/control identifier. Controls may use deterministic IDs derived from case, engine, and route.

`source_sql_path`: canonical path to the source SQL used for this row.

`candidate_sql_path`: canonical or run-output path to the candidate/control SQL when applicable.

`generated`: whether a candidate was generated by a method or imported from retained evidence.

`ready`: whether the row was ready for the relevant downstream gate.

`executed`: whether execution happened in the evidence source.

`exact`: whether the candidate/control satisfied the correctness gate for the row's route and denominator.

`timed`: whether usable timing evidence is present for the row. This must remain separate from `executed`; an execution can succeed without timing evidence.

`result_status`: normalized status such as `pass`, `fail`, `unsupported`, `missing_artifact`, `not_run`, `checker_rejected`, or `timing_missing`.

`failure_stage`: normalized stage such as `generation`, `parse`, `execution`, `checker`, `plan_collection`, `timing`, or `artifact_collection`.

`failure_type`: stable failure bucket for reporting.

`parse_status`: parse/extract status for candidate SQL where relevant.

`checker_status`: checker outcome such as `pass`, `reject_expected`, `reject_unexpected`, `not_applicable`, or `not_run`.

`plan_available`: whether retained or generated plan evidence is available.

`plan_artifact_path`: public-safe retained plan path, sanitized public copy, or private/archive reference.

`latency_ms`: timing value when retained and eligible. Blank/null does not imply zero.

`speedup`: derived speedup value when retained and eligible. This draft does not authorize computing or changing speedup.

`timing_eligible`: whether the row is eligible for timing interpretation under the metrics contract.

`evidence_source`: source class such as `canonical_case_package`, `retained_legacy_report`, `retained_legacy_run`, `user_run`, or `adapter_import`.

`retained_artifact_path`: path or reference to retained evidence supporting the row.

`notes`: concise boundary or caveat text.

## Adapter Requirements

Retained evidence adapters should:

- read from canonical case packages, `evidence/runs_retention.yaml`, aligned case sets, and curated reports/results maps;
- preserve denominator and route labels without inferring new membership;
- mark local-path, raw-log, prompt/model, timing, and scratch artifacts as review-required unless already sanitized;
- avoid writing into case-local `runs/`;
- avoid recomputing metrics unless the metrics contract and maintainer approval authorize it.

## Reporting Boundary

The ledger should support future reports that are:

- denominator-aware;
- role-aware;
- failure-aware;
- timing-eligibility-aware;
- explicit about retained evidence versus newly generated user output.

This draft is not a result table and does not authorize paper table changes.
